## 집 컴퓨터에서 이어할 순서

### 1. 프로젝트 작업 브랜치 받기

이미 프로젝트가 있다면 해당 폴더에서 다음 순서로 확인합니다.

```sh
git status --short --branch
git fetch origin
git switch codex/operations-backend
git pull --ff-only
```

첫 명령에서 저장하지 않은 변경이 보이면 이후 명령을 실행하기 전에 멈추고 확인합니다. 기존 작업을 덮어쓰거나 `reset --hard`를 사용하지 않습니다. 작업 브랜치가 원격에만 있을 때 일반적으로 자동 추적 생성되며, 그렇지 않으면 `git switch --track origin/codex/operations-backend`를 사용합니다.

프로젝트가 없는 컴퓨터에서는 원하는 상위 폴더에서 새로 받습니다. 기존 폴더에 덮어쓰지 않습니다.

```sh
git clone --branch codex/operations-backend https://github.com/doddak-147/contest-project.git
cd contest-project
```

### 2. 기존 방식으로 서버 로그인

평소 사용하던 SSH 접속 방법이나 클라우드 서버 접속 콘솔을 이용합니다. 비밀번호·인증키 원문은 채팅이나 Git 저장소에 올리지 않습니다.

```sh
ssh 사용자명@서버공인IP
```

인증 방식은 기존 설정을 따릅니다. 키 파일 방식이면 키 내용을 붙여넣는 것이 아니라 SSH 명령의 `-i`로 로컬 파일 경로를 지정합니다. 서버 프롬프트가 `ubuntu@서버이름:~$` 또는 `root@서버이름:~#`처럼 표시되는 상태에서 다음 명령을 실행합니다. 클라우드 인증키 파일과 SSH 로그인용 키가 같은 용도라고 가정하지 말고, 기존에 성공했던 방법을 사용합니다.

### 3. 서버에서 조회만 하기

```sh
free -h
df -h /
ss -lnt
docker --version
docker compose version
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
```

이 명령들은 조회용입니다. Docker 미설치나 권한 오류가 나오면 결과 그대로 확인하며, 설치·권한 변경·재시작은 진행하지 않습니다.

결과와 함께 다음 정보만 공유하면 됩니다.

- 현재 운영 중인 서비스의 주소
- 이 프로젝트에 사용할 도메인·서브도메인 보유 여부
- 알고 있다면 기존 웹서버가 Nginx·Caddy인지, 컨테이너로 운영 중인지

### 4. 결과 확인 후 배포 방식 결정

1. 메모리 1GB·디스크 10GB에서 기존 서비스와 함께 운영할 여유가 있는지 판단합니다.
2. 앱 내부 포트와 Compose 프로젝트명·DB·볼륨을 기존 서비스와 분리합니다.
3. 기존 80/443 웹서버가 있다면 유지하고 새 서비스 연결 방식을 결정합니다. 현재 Compose의 Caddy를 그대로 켜면 포트가 충돌할 수 있습니다.
4. 서버·도메인·프록시 구성과 변경 범위를 확인한 뒤 실제 배포를 진행합니다.
5. HTTPS, 로그인, 자동 수집, 백업, 외부 접속과 기존 서비스 정상 동작을 확인합니다.

상세 배포 절차는 [운영 가이드](operations.md)를 참고합니다. 서버 정보를 확인하기 전에는 해당 문서의 전체 기동 명령도 바로 실행하지 않습니다.
