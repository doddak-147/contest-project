# 전산직 포트폴리오 정리

## 프로젝트 소개

> 여러 공모전 사이트의 데이터를 통합하고 지원 기록을 관리하는 서비스를 개발했습니다. 단순 목록 제공에서 더 나아가 데이터 품질, 사용자별 권한, 변경 추적, 장애 시 데이터 보존, 백업·복원과 운영 가시성을 고려했습니다.

기술 구성은 HTML/CSS/JavaScript, Python/FastAPI, SQLAlchemy/Alembic, SQLite 개발 환경과 PostgreSQL 운영 구성, Docker Compose, GitHub Actions입니다. 공개 배포와 PostgreSQL 운영 검증은 아직 완료하지 않았으므로 실제 운영 경험으로 표현하지 않습니다.

## 설명할 수 있는 문제 해결

| 문제 | 구현한 대응 | 보여줄 근거 |
| --- | --- | --- |
| 많은 공고를 한 번에 로딩 | 서버 검색·필터·24개 페이지네이션 | 목록 화면, API 응답의 total/page/pages |
| 사이트마다 공고 중복·마감일 차이 | 보수적 통합·별칭·원본 보존·충돌 검토 | 출처 링크, 관리자 검토 목록, 수집기 테스트 |
| 마감 후 준비 기록 소실 | 공고 영속 보존과 계정별 지원 보드 | 종료 공고 조회, 메모 보존 테스트 |
| 브라우저·기기마다 기록 분리 | 서버 저장과 명시적 비회원 기록 가져오기 | 로그아웃·재로그인 시연, 계정 분리 테스트 |
| 동시 수정으로 메모 덮어쓰기 | version 조건 UPDATE와 409 응답 | 오래된 버전 수정 거절 테스트 |
| 외부 사이트 오류·중복 수집 | 성공 데이터 보존·실행 잠금·지문 기반 재반영 방지 | 실패 복구 테스트, 실행 이력 |
| 관리자 작업 근거 부족 | 서버 권한 검사·검토 메모·감사 로그 | 일반 계정 접근 거절, 검토 후 감사 기록 |
| DB 손상·복구 가능성 불명확 | 체크섬·건수·세션 폐기를 확인하는 별도 DB 복원 | 실제 SQLite 복원 보고서 |

## 면접 시연 순서 (약 5분)

1. 통합 목록에서 출처·접수 상태를 바꾸고 다음 페이지로 이동합니다.
2. 비회원으로 찜한 뒤 가입하고, 사용자가 선택해서만 계정으로 가져오는 것을 보여줍니다.
3. 메모·준비 단계·체크리스트를 저장하고 로그아웃·재로그인으로 서버 저장을 확인합니다.
4. 일반 계정의 관리자 API 접근 거절과 관리자 계정의 운영 화면을 비교합니다.
5. 충돌 원문을 비교해 검토 근거를 저장하고 감사 로그를 확인합니다. 검토가 원본 강제 수정은 아님을 설명합니다.
6. 테스트·복원 보고서로 데이터 보존과 복구 검증을 설명합니다. 실제 운영 중인 수집을 불필요하게 실행하지 않아도 됩니다.

## 수치와 표현 범위

2026-11-03 스냅샷 기준 출처 원본 574건을 통합해 509개 공고로 제공했습니다. 이는 전체 공모전 시장의 수집률이나 사용자 수가 아닙니다. GitHub Actions에서 자동 테스트 36개와 브라우저 시나리오 9개, Docker 이미지 빌드를 통과했고, SQLite와 PostgreSQL에서 509개 공고의 복원 결과를 검증했습니다. PostgreSQL에서는 계정·메모 보존, 세션 폐기, 복원 DB에 연결한 앱 기동도 확인했습니다. 실제 측정과 실행 방법은 [검증 기록](verification.md)에 있습니다.

“무중단 운영”, “고가용성”, “대용량 트래픽 검증”, “운영 PostgreSQL 복구 완료”는 현재 결과로 주장할 수 없습니다. 배포 구성·CI는 준비했지만 실제 서버 적용과 실행 이력은 별도 확인 대상입니다.

## 다음 발전 단계

첫째, 실제 서버·도메인에서 HTTPS 배포와 PostgreSQL 복구 훈련을 진행합니다. 둘째, 외부 저장소 백업·복구 목표·보관 정책과 장애 알림을 추가합니다. 셋째, 측정한 트래픽과 검색 지연을 근거로 인덱스·검색 방식·작업 큐 도입을 판단합니다. 기능 개수보다 운영 문제를 어떻게 재현하고 검증했는지 설명하는 데 초점을 맞춥니다.
